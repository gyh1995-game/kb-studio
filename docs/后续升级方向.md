## 0. 你现在接手的是什么

**KB Studio** —— 一个本地跑、零构建、离线可用的「链接 → 知识卡」消化工作台。
用户的原话定位：**痛点不是"存不下来"，是"存了再也不看"。**

| 项 | 事实 |
|---|---|
| 仓库 | `https://github.com/gyh1995-game/kb-studio`（public） |
| 代码根 | `KB-Studio/`（**这一层就是仓库根**，不是它的父目录） |
| 后端 | `server.py`，约 2400 行，**只用 Python 标准库**（`http.server`），无框架、无数据库 |
| 前端 | `static/index.html` + `static/app.js`（约 3000 行）+ `static/app.css`，**原生 JS，无构建步骤** |
| 抓取层 | `fetchers.py`，约 1600 行，知乎/抖音/小红书/B站/公众号/ins/fb/网页/本地文件 |
| 数据库 | **就是那个 Obsidian 库本身**：markdown + YAML frontmatter。没有第二份存储 |
| 跑起来 | 双击 `启动知识库.bat`，或 `python server.py` → `http://127.0.0.1:8777/` |
| 依赖 | `requests` + `beautifulsoup4`（核心）；`yt-dlp` + `faster-whisper`/`funasr`（视频，可选） |

### 0.1 四条不可协商的约束（违反任何一条，改动就是错的）

1. **开源可复现**：任何要装到全局 Python 的依赖，必须同时进 `requirements.txt` **和**
   `tools/install.py`。换一台机器要能一条命令跑起来。
2. **入口是"丢链接"，不是"检索"**：不要主动去平台搜索、不要加批量采集、不要做爬虫式监控。
   除非用户明确说"去调研"。
3. **本地 / 离线 / 零构建**：**禁止** npm、打包器、CDN、外链字体、外链图片、外链脚本。
   要图就放本地文件。这条会直接卡住第 5 节的 3D 方案，先看那里的说明。
4. **可逆优先**：删除走 `inbox/trash/`，不物理删；批量改文件先备份，且改完能拿出单份 diff。

### 0.2 凭据红线

- `KB-Studio/cookies/`、`config.json`、`uploads/`、`media/` 已被 `.gitignore` 挡住，是**真实登录凭据**。
  **任何 git 操作前先确认 `.gitignore` 还在**，任何提交前跑一次
  `git status --short` 确认没有 `cookies/`。
- **绝对不要把用户的 cookie 写进代码、配置、文档、日志或对话。**
- 临时凭据只放库外目录（`KB_COOKIE_DIR` 环境变量指过去）；端到端测试用 `--vault` 指到
  `%TEMP%` 下的空库，跑完 `rm -rf` 并用 `find` 复查无残留。

### 0.3 信息架构铁律：一条信息只能有一个出口

用户为这件事发过三轮火。**同一个事实在一个页面上只允许出现一次，且只能有一个写入方。**
已经定好的唯一出口：

| 事实 | 唯一出口 |
|---|---|
| 各层卡有多少张 | 首页 `#tiers` |
| 今日到期条数 | `#dueCnt`（首页 DUE 那一格与它同判定：`due <= 今天`） |
| 层级定义与准入判据 | 首页 `#ladderCopy` 一处 |
| 原料长成了哪些卡 | 卡文件 frontmatter 的 `from_raw`，前端现算 |
| 反向链接 | 只在 **wiki 卡** 的右栏；**原料页不显示反向链接** |
| 出处 | 卡正文一行 `出处：[[原料标题]]`，由 `write_card()` 写 |
| cookie 台账 | 消化页「Cookie 通行证」一块 |
| 字数 / 时长 | `count_words()` / `est_minutes()` 一把尺 |
| 提示词 | 只在 `server.py`；`docs/提示词全集.md` 是**生成的** |
| 建卡表单 | 全站只有一份（阅读页右栏「补一张卡」） |

**新增任何区块之前，先想清楚它替代谁，而不是叠加谁。**

### 2.3 技术方案（按我们的约束定死）

**数据放哪 —— 这是这个升级最关键的决定。**

我们有两种"每日数据"，来源不同，**不要混成一个东西**：

| 数据 | 存哪 | 为什么 |
|---|---|---|
| **实际发生的**（读了哪张、停留多久、勾了哪条复习） | 已经存在：`localStorage` 的 `kb.readlog.v1` + `inbox/已完成任务.json` | 本机行为，换设备本来就该从零开始，写进笔记就是污染 |
| **计划**（用户自己添加的待办、到期提醒） | **必须落盘**：新建 `inbox/plans.json` | 计划是用户资产，换浏览器丢了就是丢了他的东西 |

⚠️ **已知缺陷，做这个升级时一并修**：`kb.readlog.v1` 在 localStorage 里，
意味着**日历只能画出这台浏览器见过的历史**。换浏览器、清缓存、用无痕窗口，日历就是一片空白。
建议：给 `readlog` 加一个**回流机制** —— 每次 `dwellFlush()` 攒够若干条后
`POST /api/dwell`，服务端把「哪天读了哪张卡多少秒」追加进 `inbox/dwell-log.json`
（**这是台账文件，不是笔记，不进 `raw/` 也不进 `wiki/`**）。前端仍以 localStorage 为主，
服务端那份作为跨设备兜底和日历数据源。这是"一条信息只有一个出口"的例外，
必须明确写清谁是主、谁是从：**localStorage 是主，落盘是从**。

**日历本体：CSS grid，不引任何库。**

- 一个月 = 7 列 × 6 行的 `display:grid`。每格一个 `<button>`，`data-d="YYYY-MM-DD"`。
- 格子里显示：日期数字 + 一个热度点（当天学习分钟数分 5 档，用 `background: color-mix(...)` 配现有皮肤变量）。
- 格子右上角一个小角标：当天**未完成计划数**（来自 `plans.json`）。
- 点某一天 → 下方"这一天的明细"面板刷新：读了哪几张卡（可点开跳正文）、
  勾掉了哪几条复习、哪几条计划到期没做。
- 月份切换用 ‹ › 两个按钮，**不要**做成年历/周视图切换器（超出需求）。
- 移动端（≤760px）日历整块降级成"最近 14 天的一列条形"，不要横向挤压格子。

**方案 A 的具体形状**（走 A 就照这个来，字段一个都别多加）：

```json
// inbox/plans.json
{ "plans": [
  { "id": "p20261011-01", "text": "把 Loop Engineering 那篇的三条疑问想清楚",
    "due": "2026-10-13",           // YYYY-MM-DD，必填
    "at": "20:30",                 // HH:MM，可空 = 只按日提醒
    "path": "wiki/questions/…",    // 可空：关联某张卡，点开直接跳
    "done": false, "done_at": "" }
]}
```

- 新增 `GET/POST /api/plans`（照 `tasks()` / `write_tasks()` 现成的读写模式写，别另起一套）。
- 界面上放一块「计划」：输入框 + 日期 + 时间 + 可选关联卡片。
- **计划 ≠ 复习条目**。复习队列是系统生成的，计划是用户手写的。两者在日历里
  分开两种角标，**不要合并成一个列表**（合并了就没法分别勾选和分别统计）。

**待办/计划：先做一个决定 —— 存 JSON 还是存 markdown。**

这是个真正的分岔，选错了以后要迁移，所以**先问用户再动手**：

| 方案 | 长什么样 | 好处 | 代价 |
|---|---|---|---|
| **A. `inbox/plans.json`**（推荐先做这个） | 一个 JSON 数组 | 实现最快，字段随便加，我们现有 `tasks()`/`write_tasks()` 就是这套模式 | Obsidian 里看不见待办，等于计划层游离在库外 |
| **B. markdown + Tasks 插件的行内 emoji 格式** | `- [ ] 想清楚 Loop 那篇 #task ➕ 2026-10-11 📅 2026-10-13 🔁 every week` | **和 Obsidian 生态互通**：他装 Tasks 插件就能直接看、直接勾；我们读同一个文件不用第二份存储 | 解析要照抄它的正则，emoji 有坑（见下） |

Obsidian Tasks 插件（`obsidian-tasks-group/obsidian-tasks`，MIT，4.0k★）的**真实写入格式**，
官方文档：`https://github.com/obsidian-tasks-group/obsidian-tasks/blob/main/docs/Reference/Task%20Formats/Tasks%20Emoji%20Format.md`

```
➕ 创建   ⏳ 计划   🛫 开始   📅 到期   ✅ 完成   ❌ 取消
🔁 every day when done        重复
🔺 ⏫ 🔼 🔽                   极高→极低优先级
🆔 dcf64c                     id
⛔ dcf64c,0h17ye              依赖
```

它的解析正则（逐字抄自 Kanban 的 `src/parsers/helpers/inlineMetadata.ts`，
`https://github.com/community-archive/obsidian-kanban/blob/master/src/parsers/helpers/inlineMetadata.ts`）：

```
dueDateRegex      = /[📅📆🗓] *(\d{4}-\d{2}-\d{2})/u
recurrenceRegex   = /🔁 *([a-zA-Z0-9; !]+)/u
priorityRegex     = /([🔺🔼⏬])\uFE0F?/u
```

**已知的坑，走 B 方案必须避开**：
- NBSP（不间断空格）会让解析失败（Tasks issue #606）—— 我们前端拼字符串时别用 `\u00a0`；
- 手打的 `⏫` 带变体选择符 `\uFE0F` 时不识别（issue #2273）—— 正则里那个 `\uFE0F?` 就是为这个；
- **字段顺序有意义**（issue #1505），别乱排；
- Tasks 也支持 Dataview 的行内格式 `[due:: 2023-04-07]`，但**一次只能读写一种**，别混。

为什么它们用行内而不是 frontmatter —— Dataview 官方说得很直白：
「在任务或列表项上你能拿到 YAML frontmatter 的信息，但**没法给某一个列表项单独加**」
（`https://blacksmithgu.github.io/obsidian-dataview/annotation/add-metadata/`）。
**这条也解释了我们为什么把 `status`/`tags` 放 frontmatter（文件级），把批注放行内（块级）** —— 同一个道理。

> 建议：**先做 A**（`plans.json`），但把「导出成 Tasks 格式写进 `inbox/plans.md`」
> 留成一个 30 行的小函数。这样他不装任何插件也能在我们的界面里用，
> 哪天想在 Obsidian 里直接勾也有路，且不用重做数据模型。

参照物里那几个功能的**存储模型**（照抄思路，别照抄实现）：

| 插件 | 数据放哪 | 我们该怎么学 |
|---|---|---|
| Full Calendar（`community-archive/obsidian-full-calendar`） | 两种模式：① 本地日历 = **每个事件一个独立 md**，时间在 frontmatter，文件名被插件管成 `<YYYY-MM-DD> <事件标题>.md`；② 每日笔记日历 = **每个事件是一条列表项**，元数据走 Dataview 行内字段 | 我们的「一天一格」用第②种更轻：不生成一堆小文件 |
| Kanban（GPL-3.0，已转 `community-archive`，README 说在找新维护者） | board 就是普通 markdown：`## 列名` + `- [ ] 任务` | 如果以后要做「按状态分列」的看板视图，**用 markdown 存，别存 JSON** |
| Periodic Notes（`liamcain/obsidian-periodic-notes`） | 纯**文件名日期约定**：周 `gggg-[W]ww`、月 `YYYY-MM` | 我们的周/月汇总直接按文件名算，不要建索引表 |
| Simple Time Tracker（`Ellpeck/ObsidianSimpleTimeTracker`, MIT） | 时间数据是**笔记里的一个 ```simple-time-tracker JSON 代码块**，只存时间戳所以重启不丢 | 「计时回流到卡片」的干净做法：代码块存原始时间戳，界面现算 |
| Pomodoro（`eatgrass/obsidian-pomodoro-timer`, MIT） | 自动写进日记：`**WORK(25m)**: 20:16 - 20:17` | 要挂番茄钟就用这个格式，别自创 |
| Heatmap Calendar（`Richardsl/heatmap-calendar-obsidian`, Apache-2.0, 962★） | 日记里打 Dataview 字段 → 插件收集后画热力图 | 印证了我们的做法：**热度数据来自日记/台账，不是另建一张表** |

**日历本体：CSS grid，不引任何库。**

GitHub 的贡献图**实测渲染出来的结构**（抓 `https://github.com/users/<user>/contributions?from=…&to=…`
返回的 HTML 片段，不是猜的）：外层 `div.ContributionCalendar`，内部是 `<table>`，
每格是

```html
<td class="ContributionCalendar-day" role="gridcell" tabindex="0"
    data-date="2026-01-04" data-level="0" data-ix="1"
    aria-describedby="contribution-graph-legend-level-0">
```

**所以数据形状就是：按周成列、列内 7 行、每格 `{date, count → level 0..4}`。**
我们用 CSS Grid 复刻：`grid-auto-flow: column; grid-template-rows: repeat(7, 11px);`
（MDN CSS grid layout）。无障碍照抄它的 `role="gridcell"` + `aria-describedby` 图例。
⚠️ 网上那几篇「零依赖 GitHub 热力图」教程其实都 `npm install cal-heatmap` —— **没有权威公开的
无依赖范式，得自己写**，上面那个数据形状够你写了。

- 格子里显示：日期数字 + 热度点（当天学习分钟数分 5 档，用 `color-mix()` 配现有皮肤变量）。
- 右上角小角标：当天**未完成计划数**。
- 点某一天 → 下方明细刷新：读了哪几张卡（点开跳正文并高亮，复用 `openCard(path, anchor)`）、
  勾掉了哪几条复习、哪几条计划到期没做。
- 月份切换 ‹ ›，**不要**做年历/周视图切换器。
- 移动端（≤760px）降级成"最近 14 天一列条形"，不横向挤压格子。

**到点提醒（只做电脑端，微信是第 4 节）—— 这一节的结论全部核实过：**

✅ **`http://127.0.0.1:8777` 是 secure context**，可以弹通知。MDN 把 `127.0.0.0/8`、`::1/128`、
`localhost` 列为 "potentially trustworthy"
（`https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts`），
`Notification` 构造函数要求 secure context。
- 权限**必须由用户手势触发**：MDN 明说应在 click handler 里调 `requestPermission()`。
  放在「开启提醒」按钮里，**不要在页面加载时偷偷要权限**。
- 移动端 `new Notification()` 直接抛 `TypeError`，要用 `ServiceWorkerRegistration.showNotification()`。
  我们主要在用桌面，但代码里要 try/catch 并回落到页面内提示。

⚠️ **能力边界，必须写进界面文案**：
- **关掉标签页什么都不会发生。** 跨关闭只有 Push API 能做到，而 Push「必须有活跃的 service worker」
  （`https://developer.mozilla.org/en-US/docs/Web/API/Push_API`）—— 我们没有服务端推送，做不到，别假装做得到。
- **后台节流**：MDN 写明「不可见 >5 分钟 + 静默 >30 秒 + 高嵌套 + 无 WebRTC」时
  「**这个状态下定时器每分钟才检查一次**」（`https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout#reasons_for_longer_delays_than_specified`）。
  Firefox 桌面后台页最小 1s、Android 15min 且可能直接卸载页面。
- **休眠/挂起期间的定时器行为没有权威文档**（未核实），别承诺"到点必达"。

🔧 **因此实现上有一条硬规矩**：**不要用 `setTimeout(fn, 绝对时刻-现在)`**。
改成每次 tick 用 `Date.now()` 扫一遍到期项，并且在 `visibilitychange` 和页面加载时补发一次。
这样节流/休眠/改系统时间都不会漏，最多晚一分钟。
错过的事件汇总成一条「你错过了 N 条」，**不要逐条轰炸**。

💻 想要"浏览器没开也能响"：**纯标准库可行的一条路**是 `subprocess` 调 PowerShell
触发 WinRT 的 `Windows.UI.Notifications.ToastNotificationManager`
（API 存在：`https://learn.microsoft.com/zh-cn/uwp/api/Windows.UI.Notifications.ToastNotificationManager`）。
- **不要**引入 `win10toast` / `burnttoast10` 这类 pip 包（会拖进 pywin32，违反约束 1）。
- 品牌/归属靠 AUMID，没有它 toast 会显示成 "PowerShell"。
- 备选：`ctypes` 调 `user32!MessageBoxW`（模态、阻塞，适合"必须看到"但不适合频繁提醒）；
  或 tkinter 置顶窗。
- `msg.exe` **不要用** —— 官方定位是 Remote Desktop Session Host 用的，需要 Message 特殊权限。
- **真正"到点必达"的正确答案是 Windows 任务计划程序 `schtasks`**：
  注册一个任务去跑 `python tools/remind.py`，由它弹 toast。这是唯一不依赖浏览器开着的方案。
  （`https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks`）
- **如果上面这些在你的环境里不稳，就只做浏览器通知，并在文档里写明原因** ——
  不要为了"看起来更牛"留一个不稳的分支。

### 4.4 我们的架构约束（决定方案形状）

- 现在是 `127.0.0.1:8777` 的**本地单机服务，没有任何鉴权**。
- 走 **Webhook** 就必须有公网 HTTPS 端点 → 前置条件是"部署到网站"（用户自己也这么说了）。
- 走 **长连接 / 长轮询**（企业微信智能机器人 或 iLink）**不需要公网**，本机就能起 ——
  这条改变了原来的判断，**应该优先试它**。

因此三步，顺序可以调，但**鉴权那一步不能跳**：

1. 先给本地服务加一层**鉴权**（一个本机生成的 Bearer token）。任何对外通道接进来之前
   没有鉴权就是裸奔。
2. 做**收件箱抽象**：统一入口 `POST /api/inbox {from, text, attachments}`，
   内部按下面的规则分流。通道层（企业微信长连接 / iLink / Webhook / 邮件）只做协议翻译，
   **不碰业务**。
3. 接一个具体通道。**每接一个都要先拿一个测试号跑通收发闭环**，再谈功能。

### 4.5 「是待办还是原料」的分流判据（这条要能测）


### 5.2 执行方必须先回答的三个问题（**答案已经查过，照这个做，别重新猜**）

**① 零构建约束下，3D 引擎从哪来？—— 可以 vendor，但不是"一个文件"。**

- Three.js 是 **MIT**（`LICENSE`，© 2010-2026 three.js authors），
  把副本放进我们仓库**是允许的**，只需保留版权/许可声明。
  `package.json`：`"version": "0.186.0", "license": "MIT", "type": "module"`。
- ⚠️ **`three.min.js` / UMD 版已经被删了**。现在 `build/` 里只有
  `three.cjs` / `three.core.js` / `three.module.js` / `three.tsl.js` / `three.webgpu.js` /
  `three.webgpu.nodes.js`。`three.module.js` 658 KB（gzip 131 KB），
  且它 `import` 依赖同目录的 `three.core.js` 1.46 MB（gzip 267 KB）
  → **vendor 要落 2 个文件，约 2.1 MB**。
  （社区确认 UMD 移除的讨论：`https://discourse.threejs.org/t/umd-version-of-three-js-v-161/60912`）
- **关键约束**：ESM 要用 `<script type="module">` 加载，而 MDN 明确写
  「如果你用 `file://` 在本地打开 HTML，会因为 JavaScript 模块的安全要求遇到 CORS 错误，
  **必须通过服务器测试**」（`https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules`）。
  我们的服务是 `http://127.0.0.1:8777`，**走服务就合规**（无 npm、无 CDN、无构建）；
  但**双击 HTML 打开会白屏**，而且服务端必须给 `.js` 返回正确的 MIME 类型
  （检查 `server.py` 的静态分发，别只认 html）。
  → **如果用户要求"双击就能看"，Three.js 这条路直接不成立，只能退回经典脚本方案。**
- 更小的替代（都在零依赖范围内）：
  **CSS 3D**（`perspective` / `transform-style: preserve-3d` / `backface-visibility`，
  `https://developer.mozilla.org/en-US/docs/Web/CSS/transform-style`）做"房间"其实很够；
  raw WebGL（`https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API`）；
  或 **canvas 伪 3D 等距投影** —— 零依赖、文本标签最清晰、性能最稳，
  而且我们现有的图谱视图已经是这个路子。
- OrbitControls 这类 examples 里的模块**不能直接拿来用**（要么自己内联实现，要么用 `.cjs` 版）。

**② 我们的数据怎么映射到空间，而且用户看得懂？**
用户已经有一个能用的图谱视图（`static/` 里的 canvas 3D 邻域聚焦）。
**3D 工作台不能只是把图谱放大成"一个房间"**。建议映射：
- **空间 = 层级**：原料区（书架/仓库）→ 概念区 → 连接区 → 问题区，四个可走动的房间或四个岛；
- **物件 = 卡片**，物件大小 = 正文字数（`chars`，注意是净字数不是文件字节数），
  发光强度 = 今日是否读过（读过的数据在 `kb.readlog.v1`），标签 = 悬浮显示；
- **未读原料**在仓库里堆着，视觉上"积灰" —— 这直接呼应他的核心痛点"存了再也不看"；
- **点击物件 = 打开现有阅读页**（复用 `openCard(path)`，**不要重写一套阅读界面**）；
- 顶部 HUD 显示总量 / 各层数量 / 今日进度（复用现有 `/api/stats`，不要新造接口）。

**③ 性能底线和降级方案？**
- 瓶颈是 **draw call**。大量同形物体必须合并成 `InstancedMesh`
  （`https://threejs.org/docs/#api/en/objects/InstancedMesh`；
  值不值得用要看实例数量：`https://discourse.threejs.org/t/when-is-instancedmesh-worth-it-in-three/62044`）。
- **不要引用"几千个节点才会卡"这类数字 —— 查不到权威来源。**
  用 `renderer.info` 在真机上实测，把 calls / triangles 打出来定阈值。
- 距离 LOD、视锥剔除、静止时停 `requestAnimationFrame`
  （现有 `graph.loop()` 已经是这个模式，照抄它的 `if (!self.on) return`）。
- **必须有降级**：`prefers-reduced-motion` 或 WebGL 不可用时，回落到现在的 2D 卡片页，
  并明确告诉用户"3D 已关闭"。**3D 是加法，不是替代** —— 用户原话"除了保有当前形式之外"。
- ⚠️ **参照物本身不可复用**：所谓 **GPT-6 Astra** 是模型生成的演示合集
  （报道 `https://eu.36kr.com/en/p/3968319085523209`、示例仓库 `https://github.com/yangqiong/gpt6-astra-3d`、
  合集 `https://dev.to/valyuai/25-gpt-6-astra-creations-every-developer-should-see-and-how-to-enrich-them-with-real-world-datasets-d53`）。
  **没有可复用的官方库或 API 规范**，"房间/星球、悬停、切相机"这些交互细节**无一手文档**。
  所以 §5.1 那段提示词要的是**方法论**（先方案后实现、分阶段交付、保留前后截图），
  不是可以照抄的技术方案。


### 5.3 建议的实施节奏（照参照物那套，因为它是对的）

1. 先出 **2–3 个场景方案**（文字 + 一张示意图即可，不要一上来建模）让用户选；
2. 选定后先打通 **"连上真实目录 → 显示数量 → 点击打开文档"** 这一条最短链路，
   哪怕场景是一个灰盒；
3. 再补悬停反馈、镜头切换、材质灯光；
4. 每个阶段交付**可运行结果 + 改动前后截图**；
5. **全程不许修改或删除用户的任何原始知识文件**（只读 `scan_vault()` 的结果）。

## 7. 给执行方 AI 的工作方式要求

用户的工作习惯（**照做，别问第二遍**）：

1. **能点的就别给路径**。改了前端就替他打开 / 给可点链接，别让他翻文件夹。
2. **他会同时开好几条线，且不记得历史**。以文件时间戳判断哪个版本作数，别猜。
3. **外部能力断言必须先实测**。说"某服务能做 X"之前，打 API、读源码、看提交历史。
4. **批量回填这类活你自己做完**，不要烧他的 API 额度让他手点。
   要"统一"某个东西时，直接推倒重做并留备份，不要留两套并存。
5. **远端/对外可见的操作（push、建仓、发布）先问。**
   会真写库、真烧额度的路径（开始消化、上传、手写卡、改写、删除）只接线，不代跑。
6. **每轮改完必须做全套验收**（第 1 节那五条命令），并且**自己先骂自己一遍**
   （他叫「双向钢人」）：按「做得好 / 还不够」两栏写结论，然后**再迭代一轮**，
   不要交付完就停。
7. **UI 改动必须看截图**，桌面 1440×980 + 手机 560×900 全视图逐张检查黑边、溢出、重复区块。
   只看代码看不出的问题，只有图能看出来。
8. 新加一条产出规则，就要在 `tools/spec_check.py` 里同时加一条断言。
